# PP-DocLayoutV3：1×1 卷积布局转换实验，2026-11-05

本轮没有证明提速，不纳入建议开启的优化组合。共享服务器同一二进制交错测试，关闭均值 4.664902 秒，开启均值 5.274834 秒，观测耗时增加 13.07%。波动明显，不能据此断言内核在 K3 上更慢或更快。图的四个完整输出逐字节一致，CTC 三组形状也与此前已验证 GGML 版本逐字节一致。

## 改了什么

103 个普通卷积中，有 66 个满足 1×1、stride=1、padding=0、dilation=1。实验将它们的通用 FP32 im2col 改为 GGML permute 视图加连续布局复制，再使用相同的矩阵乘法和 FP32 累加。其余普通卷积、27 个直接 depthwise 卷积不变。

NCHW 输入仍需变成通道连续的矩阵布局，因此这不是零复制，也没有消除矩阵乘法。本项不改变模型精度、权重或输出语义。开关 `OCR_CONV_POINTWISE_PACK=1` 在创建会话时读取，默认关闭；正常对照保留 `OCR_CONV_POINTWISE_PACK=0`。

x86 构建服务器，4 线程绑定逻辑核 0–3，trace 关闭。同一个预转置 FP32 GGUF、同一份扫描页输入。原生逐元素与连续复制、分块拼接、Concat→Gather 简化均保持开启，只切换本项。每臂预热 1 次，正式 3 次；每状态 6 次正式结果。只计 GGML graph compute，不含模型加载、输入输出复制或后处理。

## 当前建议与未完成项

保留上一阶段预转置 GGUF，原生逐元素和连续复制，`OCR_LAYOUT_PACKED_CONCAT=1`、`OCR_LAYOUT_FOLD_CONCAT_GATHER=1`；本项保持关闭。上一阶段将 GGML 工作区从约 576 MiB 缩到约 248 MiB 的效果不受影响。不同负载下的各阶段加速百分比不可相乘。

默认 SDK 路径仍是 ONNX/EP 版面、视觉编码及 CTC，加 Q4 GGUF 文本；项目新增的 `--llama-only` 路径使用 GGML 版面/CTC、Q4 GGUF 视觉/文本。它是本项目在 llama.cpp 仓库内增加的专用图执行器，不是未修改上游 llama-server 已直接支持这些模型。

历史 K3 同一 H336×W588 视觉裁剪：ONNX FP16 1.362 秒，GGUF Q4 3.244 秒，约 2.38 倍耗时；精度、线程条件不同，属于历史观测，不是严格同精度交错结果。完整表格任务曾为 27.678 与 29.201 秒。版面 GGUF 与 EP 尚无 K3 实测差距；不能用本报告的服务器秒数代替。

下一步应先在获准恢复板端推理后，验证 RVV 复制漂移修复及小输入输出一致性，再对同一实际输入做 GGML/EP 计时。硬件优化重点仍是剩余矩阵乘法、卷积布局与 IME2/TCM 分块，随后才是大掩码 Where/Cast/Greater。要达到 EP 的 INT8 路径速度，需要量化校准、算子支持、硬件调度和端到端验证，不能仅更换 GGUF 容器。

本轮 K3 仅交叉编译版面 CLI/动态库，没有部署或推理；未修改服务、未更新飞书、未提交或推送源码。板端完整 SDK 和原生 PDF 15 秒／扫描 PDF 30 秒目标均未在本轮证明。

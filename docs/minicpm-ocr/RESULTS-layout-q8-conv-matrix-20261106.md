# PP-DocLayoutV3 GGML：Q8 卷积候选及 Q4 对照，2026-11-06

已为完整 GGML 版面执行器增加 Q8_0 卷积矩阵权重，完成服务器两个真实输入的数值、最终区域与阅读顺序诊断。扫描页 29/29 区域可对应到 FP32，平均框 IoU 0.998342、最大坐标差 1 像素。结果具备继续板端验证的价值，但尚未作为默认配置验收；本轮没有在 K3 推理，也未证明 llama.cpp 与 EP 等速。

## 代码与模型

沿用前阶段 `[M,K]` 卷积打包和显式卷积几何信息，增加 Q8_0 转换、加载、矩阵乘法与路径计数。95 个普通卷积满足 K 的 32 元素块长要求，转换为 Q8_0；其他普通卷积、depthwise、投影及后处理仍保留原精度。约 128.43 MiB 的源 GGUF，Q4 卷积候选约 45.92 MiB，Q8 卷积候选约 57.92 MiB。文件大小减少不是计算加速的测量。

这不是整模型全 INT8：Q8_0 是 32 元素分块权重量化，不等同于 EP 的校准、逐通道或逐张量 INT8 方案。输入、偏置、累加、非线性及非量化权重仍可用 FP32；CPU 量化矩阵点积还会转换激活。

新增单测覆盖 6 种几何、1/2 batch、非方形卷积、步长、padding、dilation 和输入保持。FP32/Q4/Q8 路径分别用可精确表示的合成权重检查输出布局。初次 Q8 单测错误地沿用只适合 Q4 的精确量化网格，量化尺度不能精确表示，导致逐位相等断言失败；改用 Q8 精确网格后通过，未放宽真实页的数值质量指标。初次失败日志保留。

## 三处排序差异的来源

扫描页三处最终区域在 FP32 中是“图片→段落标题→正文”，Q4/Q8 中为“段落标题→正文→图片”；其余 26 处保持对应次序。单独诊断使用与验证结果哈希完全相同的四个原始输出，没有改模型或后处理。

FP32 中图片 query 0 的投票为 121，标题 query 13 也是 121，正文 query 7 为 122；SDK 按全部 300 个候选的投票排序，存在图片/标题并列。Q8 中标题 query 12 为 116，正文 query 7 为 119，图片 query 0 为 123，不存在这组三者的并列。对应对象的成对上三角排序 logit 符号一致，sigmoid 已饱和；全候选投票及候选置换改变了最终排序。

因此不能仅凭与 FP32 最终排序不同，直接宣称 Q8 阅读质量退化。并列票的默认 argsort 顺序和全候选投票也有影响。尚未修改 SDK 的排序规则，避免为通过一致性检查改变原算法；后续应使用人工阅读顺序标注，并单独验证对并列票的处理。Q4 的较大框偏差仍独立存在，不因这一发现而消失。

## 性能与硬件边界

本阶段是 x86 CPU 正确性运行，日志中的 2 次 graph 时间不构成公平 ABBA 性能对照；服务器负载波动明显，不据此报告 Q8 提速。K3 可执行文件与常驻库已交叉编译并归档，但没有部署或执行。版面执行器仍固定 CPU，未接入 SpacemiT 权重重排/缓冲区或混合调度，不能将链接成功当作 IME2/TCM 已启用。

下一步先解决混合调度下 custom 算子读取实际输入副本的问题，再接入量化权重缓冲区和 SpacemiT/CPU 调度，记录实际分派与跨后端复制；板端短测获准后核验 RVV 视觉特征稳定性及相同输入、相同线程口径的 GGML/EP 对比。原生 PDF 15 s、扫描 PDF 30 s 和纯 llama/GGML 追平 EP 均未在本轮证实。

默认完整 SDK 的版面检测、视觉编码及 CTC 仍为 ONNX/EP，文本为 Q4 GGUF。项目已有 `--llama-only` 的四组件 GGML 路径，是本仓库的专用版面/CTC 执行器加 MiniCPM llama.cpp，并非未经修改的官方 llama-server 直接支持所有模型。

历史 K3 同一 H336×W588 裁剪：ONNX FP16 视觉编码 1.362 s、GGUF Q4 3.244 s，约 2.38 倍差距；精度和线程不同，不是严格引擎对照。完整表格任务历史为 27.678 s 对 29.201 s，不能把总耗时差当作纯视觉差。PP-DocLayoutV3 仍缺 K3 上 GGML/EP 同输入性能对比，不能用 x86 数据补填。

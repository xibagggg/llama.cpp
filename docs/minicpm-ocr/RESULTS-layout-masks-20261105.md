# PP-DocLayoutV3 GGML：大掩码连续处理，2026-11-05

本轮在同一二进制、同一模型和扫描输入上观测到均值 4.721226 → 4.117275 秒，耗时变化为减少 12.79%。这是共享 x86 服务器的交错测试结果，不是 K3 提速幅度。表格和扫描页的四个完整输出，与此前接受的 GGML 结果逐字节一致。

## 改了什么及适用边界

此前 Greater、Cast、Where 使用通用多维逐元素路径，每个元素重复求坐标和步幅，并由不同线程交错写入。模型的大掩码是 `[1,300,200,200]`，即 1200 万元素；输入实际是连续数组或标量。

新增 `OCR_LAYOUT_PACKED_MASKS=1`，在会话创建时读取，默认关闭。满足类型、形状、连续性、偏移、地址范围条件时，直接按连续区间分配给线程：FP32 Greater 比较，bool/I8 Cast 到 FP32 或 I64，bool 条件的 FP32 Where 选择。构图时检查资格，执行时免去逐元素多维坐标计算。一般广播、非连续步幅、其他类型保留原有回退。I64 Greater 仍走原路径。

没有融合或删除计算图节点，没有减少掩码尺寸、截断检测候选、修改阈值或更改模型精度。Where 的选择保持 FP32 值，Cast 保持原数值语义。连续分段使相邻输出主要由同一线程写入，但本轮没有用硬件计数器量化缓存失效或 DDR 流量。

## 当前边界与下一步

本轮仍为 FP32 CPU。没有完成 IME2/TCM 硬件覆盖，也未证明纯 GGML 追平 EP。后续应优先完成获准后的 K3 小样本正确性、视觉特征重复性和同输入 GGML/EP 对照，再依据板端矩阵乘法、卷积布局和数据搬移开销安排 IME2/TCM 内核优化。

默认完整 SDK 仍用 ONNX/EP 跑版面、视觉和 CTC，文本为 Q4 GGUF；项目新增 `--llama-only` 则用 GGML 版面/CTC 与 Q4 GGUF 视觉/文本。新增的是 llama.cpp 仓库内专用图执行器，不是未修改上游 llama-server 的直接模型支持。版面 GGML/EP 尚无 K3 对照，不能使用服务器结果填入该缺项；历史视觉裁剪 ONNX FP16 1.362 秒、GGUF Q4 3.244 秒也存在精度和线程口径差异。

K3 本轮只交叉编译，没有部署、推理或修改服务。未更新飞书，未提交或推送源码。原生 PDF 15 秒、扫描 PDF 30 秒与板端完整 SDK 尚未在本轮验证。恢复板端短测的确认仍待用户回复。

# 卷积打包融合：真实 GGML 调度与执行检查，2026-11-06

已验证卷积打包候选的匹配规则在 GGML scheduler 建立输入副本、拆分计算图之后仍能工作；同时检查了跳过完整 FP32 展开张量的可移植执行路径。32 组小图配置、96 次计算通过，显式输出和共享分支保持正确。前阶段 IM2COL 后端迁移的四组回归也通过。

这些是构建服务器上的调度与数据流检查，不是 K3 或完整 PP-DocLayoutV3 性能验收。本轮只增加测试设备的图检查入口、调度测试与源码跟踪规则，没有修改融合计算内核、部署板端或写飞书。

## 这轮验证补充了什么

前阶段已经在真实模型原图中找到 95 个满足形状和使用次数条件的卷积链，并用生产 RVV 函数在 QEMU 验证了打包字节。仍有一个缺口：硬件后端收到的是 scheduler 改写后的分段图，而非原图。

本轮使用与 CPU 互不接受缓冲区类型的测试设备，促使真实 GGML scheduler 复制输入。检查回调读取实际分段图，调用生产 `ocr_im2col_pack::match` 和 `pack`；每次替换输入内容，检查副本与当次原输入一致。两个 batch 配置各重复三次，允许融合的链共匹配 12 次，输入副本逐次验证通过。

| 测试状态 | 预期与实际结果 |
|---|---|
| 展开留在 CPU、矩阵在测试设备 | 分为 3 段；设备分段中不存在可融合链 |
| 展开与矩阵同设备、单一消费者 | 分为 2 段；每次可匹配并正确读取输入副本 |
| 完整展开张量或其 Reshape 被标为输出 | 拒绝融合，输出保持 |
| 展开张量另有 CPU 分支消费者 | 拒绝融合，分支完整数据保持 |

## 执行检查的边界

测试既运行未消除展开张量的参考，也运行消除路径。消除路径实际提取四行、量化打包并调用 GGML CPU 的 Q8 点积生成矩阵输出，跳过原 IM2COL/Reshape/MulMat 三节点。全部小图矩阵输出与独立坐标卷积公式精确一致；同时验证打包字节、输入保持和设备缓冲区保护。scratch 边界由前阶段独立测试检查。可见展开输出及共享分支也独立逐值检查。

其中只有两个允许融合的配置各执行三次，合计 **6 次**真正走测试设备的消除路径；其他配置检查参考或拒绝条件。96 次是小图计算总数，不能说成 96 次完整模型融合。

测试设备使用标准 GGML Q8_0 物理格式和 CPU 点积，不执行 SpacemiT 权重重排、HP 激活布局、IME2、TCM 或实际硬件屏障。因此它补充的是生产匹配/提取函数与真实 scheduler 的连接证据；前阶段的生产 RVV 打包测试是另一项证据，二者不能合并称为板端融合验收。没有测量或推算速度。

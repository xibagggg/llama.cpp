# GGML 完整版面图算子诊断：2026-11-05

本轮仅在 x86 服务器采集算子轨迹，模型为预转置 FP32 GGUF，4 线程绑定核 0–3。预热 1 次，诊断 2 次；扫描页输入与前一阶段完全相同。该轨迹用于选择优化对象，不能当作 K3 算子耗时或 EP 对照，也不和关闭 trace 的性能均值混算。

## 跟踪完整性

原 trace 接口部分函数没有导出，且 worker 尾部小于 64 KiB 的线程局部缓冲没有写出。本轮导出相应接口，并在每个 graph 的最终 barrier 前写出所有 worker 尾部。未启用 profile 时调用是空宏。使用独立 `build-layout-profile-x86`，保留原有性能库。

每次 graph 都捕获 4 个 worker 的完整 B/E 事件，核验每条事件的配对、各 worker 算子顺序及对应 graph 节点。3 次运行的四个完整输出与既有哈希一致，输入保持，重复输出一致。没有将漏事件当成零耗时。

## 时间口径

对每个实际执行的 GGML 节点，取所有 worker 最早 begin 到最晚 end 的墙钟跨度，再对两次正式诊断取均值。不同 worker 的持续时间不相加为总耗时。该跨度包含线程被调度离开的时间和算子内部同步，不是 CPU 周期数或硬件纯计算时间。

## 优先优化对象

1. Concat 通用坐标解释执行共约 1.754 s。末尾单个 `[1,6,300,200,200]` 拼接输出 288,000,000 字节，约 1.084 s，是最慢单节点。优先将连续输入的拼接改为并行分块复制；保留非连续视图回退。
2. MUL_MAT 累计约 1.962 s，IM2COL 约 0.865 s。需要结合 K3 的实际形状与后端覆盖，再设计卷积展开、权重准备、IME2 分块及精度路径；x86 比例不能直接指导 TCM 容量或判断 K3 内核速度。
3. Where、Cast、Greater、Gather 等大掩码张量仍在通用解释循环。后续可验证广播步进、连续分块和合法图融合，保留所有输出和完整掩码语义。

仅把模型改存 GGUF 不会自动获得 EP 的图优化和硬件路径。当前 profile 仍是 FP32 CPU 基线；版面、CTC 的 IME2/TCM 覆盖与完整 K3 SDK 验收未完成。

证据：`profile/PROFILE.json` 含每轮每节点耗时、前 30 个节点和完整输出哈希；`profile/ggml_trace.json.gz` 是完整轨迹；`PROFILE-BUILD.json` 保存构建产物哈希。前面的接口链接失败日志保留，成功轨迹单独保存。

# PP-DocLayoutV3 GGML 连续拼接优化：2026-11-05

本轮按算子轨迹定位到的瓶颈，将 Concat 从逐元素坐标解释执行改成连续输入的并行分块复制。同一二进制交错测试中，服务器完整扫描页版面推理均值由 7.236079 s 降到 5.644180 s，本轮均值耗时减少 22.00%。表格裁剪和扫描整页的四个完整输出逐字节一致。

这是 x86 服务器结果。K3 候选仅交叉编译归档，未部署、未执行；没有更新飞书，没有提交或推送源码。版面仍是 FP32 CPU，不能据此声称已达到板端 EP 同速或完整扫描 PDF 30 秒目标。

## 为什么优化这里

[上一阶段完整轨迹](../20261105-layout-pretranspose/PROFILE-REPORT.md)中，24 个通用 Concat 的诊断墙钟跨度约 1.754 s，占该次 graph 约 26.10%；末尾 `[1,6,300,200,200]` 的单个拼接输出 288,000,000 字节，约 1.084 s。旧实现对每个元素拆坐标、寻找输入、计算地址并转换为 double 后写回，连续数据也承担相同开销。

## 实际改动与边界

- 只对全部输入类型一致、连续、形状匹配、轴长度之和正确、数据范围合法的 Concat 启用快速路径，支持超过四维的逻辑张量。
- 按外层行与输入片段分块，每块最多 64 KiB，由各 worker 复制互不重叠的块；保留输入偏移与尾块长度，避免逐元素坐标除法和数值转换。
- 不满足条件的非连续视图等仍使用原通用路径。独立开关 `OCR_LAYOUT_PACKED_CONCAT=1`，默认关闭；当前 C API 创建会话也读取该环境开关，应在创建会话前设置。
- 模型权重、精度、候选数量、四个完整输出和执行图结构保持。该模型的 24 个 Concat 全部满足条件。

当前仍写出完整拼接张量，计算工作区仍为 576.1719 MiB，图节点仍为 3442；不能把本轮速度提升解释为删除掩码、跳过检测层或减少内存容量。

## 性能证据

预转置 FP32 GGUF，同一共享库，4 线程绑定服务器逻辑核 0–3，关闭 trace。关闭/开启/开启/关闭；每臂预热 1 次、正式 3 次，各状态 6 次正式结果。仅计 GGML graph compute，不含会话创建、输入输出复制和 Python 后处理。每一轮都检查四个完整输出哈希、有限值与输入保持。

|---|---:|---|
| 关闭分块拼接 | 7.236079 | 6.597451–7.500260 |
| 开启分块拼接 | 5.644180 | 4.888012–6.988247 |

| 交错臂 | 分块拼接 | 三次正式耗时 s |
|---|---|---|
| 0 | 关闭 | 7.310896 / 7.490747 / 7.500260 |

| 3 | 关闭 | 7.326464 / 7.190657 / 6.597451 |

均值下降约 22.00%，但共享服务器仍有负载，第二个开启臂发生较大波动，两种模式的单次区间有重叠。因此这里只报告这次完整对照的观察值，不将 22% 作为稳定板端收益。此前预转置阶段的 13.31% 属于另一轮负载条件，不能与本轮相乘或直接合并成累计提速比例。诊断轨迹的时间也不能混入本表。

## 正确性

- 完整表格裁剪与扫描页：同一候选共享库，开/关各重复 2 次，类别 logits、300 个框、完整阅读顺序 logits、完整 masks 四组数组均与前阶段已验收哈希逐字节一致。
- 交错四臂全部预热/正式调用再次验证完整扫描页输出；输入保持；没有导入 `onnxruntime`。
- 六组四线程针对性检查覆盖五维、不同拼接轴、非零偏移、跨 64 KiB 边界及尾块、FP32、I64、布尔数据；核验输出前后 guard、输入保持，并拒绝错误轴长、越界及非连续输入的快速路径。I64 检查包含超过 2^53 的值，验证字节复制不会丢整数精度。
- 原参考模型/输入不变。完整输出相同意味着本轮的框、顺序与掩码渲染继承前阶段结果；本轮没有另行宣称 OCR 识字准确率或置信度提高。

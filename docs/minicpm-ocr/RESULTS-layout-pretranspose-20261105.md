# PP-DocLayoutV3 GGML 固定权重预转置：2026-11-05

本轮在 GGUF 转换阶段预转置固定 Gemm 权重，消除每次推理中重复的权重转置。服务器验证中，表格裁剪与扫描整页的四个完整输出均与已验收 GGML 基线逐字节一致。K3 候选已交叉编译归档，未部署、未执行；未更新飞书，也没有提交或推送源码。

## 改了什么

- `convert-doclayout-gguf.py --pretranspose-gemm` 对 137 个 Gemm 使用的 83 个唯一常量矩阵预转置，并设置 `transB=1`。有其他消费者需要原布局时保留原张量；已转置节点保持正确。默认不开启。
- GGML Gemm 构图支持 `transB=0/1`，已转置权重省去运行时 transpose + contiguous。仍为 FP32；没有减少候选、删除掩码、跳过阅读顺序或引入 ORT。
- 转换的 3 项针对性测试覆盖非方阵、共享权重和已有转置。转换审计核对全部 916 个权重张量与节点/输出。

## 可确定的图与内存变化

| 指标 | 原始 GGUF | 预转置 GGUF | 变化 |
|---|---:|---:|---|
| 运行时 Gemm 权重转置 | 137 | 0 | 消除 137 次 |
| GGML 图节点 | 3716 | 3442 | 少 274 个 |
| GGML 分配的计算工作区 MiB | 593.3599 | 576.1719 | 减少 17.1880 MiB |
| 模型文件字节 | 134667520 | 134667616 | 增加 96 字节元数据 |
| 每次推理的转置输出字节 | 40000512 | 0 | 减少约 38.15 MiB 逻辑写出 |

计算工作区来自 GGML allocator，不是进程 RSS。转置输出量是图中张量大小之和，不是硬件计数器测得的 DDR 流量；工作区复用使两者数值不同。

## 服务器计时：观察到收益，仍需板端验收

同一最新版共享库、相同扫描页预处理字节、相同 FP32 精度，4 线程绑定逻辑核 0–3。原始/预转置/预转置/原始交错；每臂预热 1 次、正式 3 次。仅计 GGML graph compute，不含加载、输入输出复制和 Python 后处理。每次运行均校验完整输出哈希、有限值及输入保持。

| 模式 | 正式均值 s | 正式范围 s | 相对原始耗时 |
|---|---:|---|---|
| 原始权重布局 | 8.921240 | 6.894708–10.635216 | 100% |
| 预转置 | 7.734153 | 6.497525–8.887674 | 86.69% |

本轮均值耗时少 13.31%。但服务器存在其他负载，前后两臂预转置均值约 8.63 / 6.84 秒，两个模式的单次范围明显重叠。不能据此确认稳定的独立提速幅度，不能作为 K3 速度，更不能据此声称达到 EP 同速或扫描 PDF 30 秒目标。保留全部慢值，不按最好一次报告。

## 正确性与适用范围

扫描整页与表格裁剪在两个模型各重复 2 次，类别、框、阅读顺序、完整掩码四组数组逐字节一致；交错计时再次核验扫描页每一轮的四组完整哈希。输入保持；推理未导入 `onnxruntime`。与 ONNX CPU 的数值和版面对应关系继承上一阶段完整验证；本阶段不声称跨引擎逐位相等。

本轮是项目内新增的 GGML 版面执行器优化，不能将模型直接交给未修改的上游 `llama-server`。版面和 CTC 仍是 FP32 CPU 基线。链接 SpacemiT 库不代表新图已经进入 IME2/TCM。
